# DeepSeek-V4.1-Flash-1017 上下文与内存预算审计（7an）

**建议下一步先验证 2048-token 上下文。** 当前 1024 限制来自本地入口的
固定校验，原生 Strata 引擎已有 `--max-context`。扩展需要让输入预算、
原生参数、READY 校验和结果记录一致，无需为此重写算子或构建新引擎。

本步只读固定源码、pack 元数据和已有日志：**0 个模型进程、0 个请求、
0 次原生构建**。当前入口仍为 1024，输出上限仍为 1–256，所有配置默认值、
20 GiB GPU、8 GiB 主机可用内存停止线、零引擎 swap 要求均保持不变。
2048 尚未实测；之前 7af 的 swap 故障仍未解决。

## 依据与边界

- 原生引擎是已测 CUDA12.8/SM75 版本，SHA256 为
  `d6d9e7cdafbd3591faa61df7915b0f9bdd2f30aee4eeacb3befabb469a1b1553`。
- 审计配置是 `memory-experimental`：36 GB 十进制 LRU、heat1、chunk256、
  RAM preload on、GPU settle1000ms、18 workers、fresh KV、DSpark none、vision off。
- 固定源码位于 `build-deepseek-cuda/step7ae-upstream/src/dsv41/`。
  已复核 7 份相关原生文件的构建输入哈希；总共固定 22 个审计输入哈希。
- pack 的 `max_position_embeddings=1048576`、原生 Options 默认 32768、
  原始 RoPE 长度 65536 是不同元数据。它们不证明本机或当前入口已通过这些长度。
- 下列容量是源码推导的分配请求，包含已知对齐；MiB/GiB 为二进制，GB 为
  十进制。CUDA/驱动记账、分配器、运行期峰值和质量需要另外实测。

## GPU：共享 KV 与工作区

40 个 decoder 复用 4 个压缩 KV source：原始层 2、8、14 的压缩比例为 2，
层 20 为 1。8 个 index-query source 层共享这些 source 的持久 key 缓存。
单 GPU 下，每个 source 只有一份压缩 KV 和一份 index-key 分配。
滑窗 ring、chunk256 的多数计算区、专家 staging ring 等不随总上下文成倍增加。

固定 pack 的压缩 KV 行为 **288 B**：512/2 个 code 字节加 512/16 个 scale
字节；index 行为 **80 B**：128/2+128/32=68 B，再按 16 B 对齐。
每个 source 行数为 `ceil(context / ratio)+1`，每份 CUDA 分配再按 256 B 对齐。
40 层各自的 FP8 window ring 行为 528 B，128-token ring 的 payload 合计
2,703,360 B，与这里选择的总上下文无关；其他固定工作区没有因此计入增量。

已核算的上下文相关 GPU 项包括共享压缩 KV/key、window 的 score/block-score、
chunk 的 index-query slab、score/block-score。`ss=context+64`；window 为
16 行，chunk 的 index slab 行数按原生公式在 32–128 间选择。本表同时计入
这个 slab 可能缩小的变化，不把源码的“约64MB”注释当成绝对上限。

| 总上下文 | 已计 GPU 容量 MiB | 比 1024 增加 MiB | cap256 下最大输入 token | 可选 LM 状态容量 MiB |
| ---: | ---: | ---: | ---: | ---: |
|1024|3.609|0.000|768|67.523|
|2048|5.140|1.531|1792|157.555|
|4096|8.203|4.594|3840|337.617|
|8192|14.328|10.719|7936|697.742|
|16384|26.578|22.969|16128|1417.992|

1024→2048 的已知 GPU 增量为 **1,605,632 B =1.53125 MiB**，其中 KV/key
增加 942,080 B，四份 score/block-score 工作区分别增加 65,536、8,192、
524,288、65,536 B；index-query slab 在这两个长度均为 128 行。
这是容量子集增量，不是新的 GPU 峰值测量。原生引擎先分配这些区域，再按
剩余 VRAM 放置专家，所以更长上下文也可能减少驻 GPU 专家数量，影响读盘和延迟。

所有权、2270 起的 window/source 分配、2814 的行大小、2858 起的 chunk
分配、3849 起的专家预算；`ds4_kernels.cuh:23` 定义压缩行格式。

## 主机：按实际提示词长度产生的临时状态

单 GPU 的 flow 路径在至少两个 chunk、预计节省读取且 RAM 预算允许时，可以
按层处理多个 chunk。它把每个 chunk 跨层的残差和索引状态保存到主机，
另分配一层专家的临时缓存。该路径是否进入还取决于自动路径选择、已驻专家、
预期读取量和当时可用内存，不能由设置 `--max-context` 单独决定。

一个 token 的状态容量为：

`4×5120×4 +8×4 +512×4 +2048×4 =92,192 B`

固定 chunk256 时，每个 chunk 的槽为 **23,601,152 B**。输入按
`nc=ceil(n/256)`、`per=ceil(n/nc)` 均分；例如 264 tokens 分为 132/132，
仍分配两个完整状态槽，合计 47,202,304 B。它与既有双 handoff 缓冲
47,202,432 B 是不同所有者，后者包含两个 allocator wrapper 的额外 64 B。

cap256 下，1024 最大输入 768，对应 3 槽、70,803,456 B；2048 最大输入
1792，对应 7 槽、165,208,064 B，状态容量多 **94,404,608 B（90.03 MiB）**。
实际输入短时按实际 chunk 数分配。相对已测 264-token 的两槽，1792-token
场景多 5 槽，不能把“上下文只多 1.53 MiB”当成整个进程的增量。

临时层缓存的 `need` 是最大一层中仍从文件读取的 CPU 专家数乘其 blob stride。
根据完整 40 层混合量化元数据，每角色对齐并加 8192 B 间隙，最大 blob 为
8,687,616 B；全 384 专家的一层容量上界为 **3,336,044,544 B（3.34 GB）**。
这不是 2048 必然新增的 RAM，也不是缓存实际占用；已测 264-token 请求就有
原生日志的 `layer-major,2 chunks,3.0 GB of RAM`，这里的 3.0 是舍入值。

原生 `lm_begin` 用当时 host/cgroup 可用量扣除 8 GiB 和状态容量后限制层缓存。
不足一个最大 blob 或预期 IO 收益不足时会放弃 LM；状态锁页失败也可以回退
pageable。两项临时分配会在 cache settling/preload 前释放并同步，成功或失败
路径均有清理。因此表中极大长度的几十 GiB 状态是“若走此路径”的容量场景；
不能据此声称它们必然分配成功，或把它当成所有原生路径的内存硬下限。

源码位置：`ds4_model.cu:7862–7935` 的条件、分配及释放；7967 起的输入划分；
8198 起的释放顺序。flow 读取 deque、调度数组、vector capacity、chunk event、
分配器和驱动等额外开销尚未完整定量，不能默认为零。

## 与已测资源对齐

7am 只测过 context1024：8 题全部 EOS，842 个资源采样，峰值 RSS 37.77 GB、
最低主机可用内存 15.14 GB，未观察到 swap；两个 264-token 请求已使用 LM。
这些样本不是 2048 的内存或速度预报；采样也不能排除未捕获的瞬时峰值。

作为容量检查，沿用 7ai 的非 store 已知容量子集 2,265,319,624 B（含满额
Engram payload，缺少部分元数据），加入 36GB store 的 35,999,744,000 B、
2048/cap256 最大输入的 LM 状态、最大一层缓存与 8 GiB floor，合计：

**50,356,250,824 B（50.36 GB）**。

这是假设这些已知容量同时驻留的场景。7am 起始 `MemAvailable` 为
52,493,484,032 B，扣除后约有 2.14 GB 供未计开销承担；起始状态和后续最低
可用量不是同一时刻，不能拼成不存在的快照。该算式既不预测实际 RSS，也不是
新准入条件、零 swap 保证或对 7af 故障的解释。当前公开入口的启动要求仍是
主机可用内存至少 8 GiB，运行中另检查进程 swap 和 GPU 边界。

## 先验证 2048 的原因及入口改动范围

默认 YOCO 模式保留最后 `(40−20)×(128−1)+128=2668` 行，至少能跳过
1024 行才启用前缀跳过，即提示词从 **3692 token** 起可能走另一条路径。
2048/cap256 的最大输入 1792 未到这个边界；4096/cap256 的最大输入 3840
可以跨过它。先验证 2048，可以把新上下文检查与更长输入的自动前缀优化分开验收。
这只说明源码条件，未验证 4096 或 YOCO 长输入质量。

未来入口需要同步六个边界：完整模板的 input+output 预算、single/file/stdin/
resident 准备路径、原生 `--max-context`、严格 READY 匹配、结果中的 context、
profile 参数拒绝与资源/清理行为。当前源码的 `prepare_case`、READY、method
及继承自 7g 的命令仍固定 1024。本步没有修改它们。

**提议下一步 7ao（尚未开始）：**

1. 为 `memory-experimental` 增加明确的 `--context 1024|2048`，默认仍为 1024；
   其他 profile 拒绝 2048。保留原引擎/pack 哈希、输出上限、模板和全部保护。
2. 先通过不启动 GPU 的旧默认命令/环境兼容、各输入源、极限/超长拒绝、
   READY 失配、记录一致和错误/取消清理检查。
3. 再最多一个原生模型、三题：短控制题、1400–1700-token 左右的跨位置记录
   抽取题、相同长题重复。实际完整输入必须超过 1024，且 input+cap128≤2048；
   题目、token IDs、期望字段和格式标准在运行前固定，每题 fresh KV。
4. 总时限 30 分钟，原有失败诊断保持最多 3 秒；任一运行、资源、驱动脚本或
   配置失配就停止并保留部分数据，不重试。记录原生实际路径、chunk 回退、
   RSS/GPU/可用量、首字、内容/格式与退出清理；不拿它当速度 A/B 或默认提升。
